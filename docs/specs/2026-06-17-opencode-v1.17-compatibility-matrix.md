## 消费面（以当前代码为准）

先厘清插件的角色：`Nook/Resources/opencode-plugin/index.js` 的 `event` hook 是**全量透传**—— opencode bus 发出的每个事件都原样转发，只额外注入 `pid` / `cwd`。它自己合成的事件只有两个：`session.started`、`serverPort`。

所以下表「生产者」列区分的是**事件由谁造**，不是「经不经过插件」——全部经过插件。

| 事件 | 生产者 | Nook 消费 | Adapter handler / 关键条件 |
|---|---|---|---|
| `session.created` | bus（透传） | yes（legacy；v1.18+ 很少发） | `handleSessionCreatedOrUpdated` |
| `session.updated` | bus（透传） | yes（主注册路径，之后只刷新 cwd） | `handleSessionCreatedOrUpdated` |
| `session.started` | **plugin 自造** | yes（resume 自愈；`provisional` = `session.list()` 猜的 id） | `handleSessionStarted` |
| `session.status` | bus（透传） | yes：`busy` / `retry`→`.processingStarted`；`idle`→flush + `.stop`（**≤1.17 会在 tool step 之间发 `idle`，该路径不支持，见陷阱 4**） | `handleSessionStatus` |
| `session.idle` | bus（透传） | yes（legacy 冗余结束信号；已 deprecated，仍可能丢失） | `handleSessionIdle` |
| `question.asked` | bus（透传） | yes（PRIMARY，带 `que_` requestId） | `handleQuestionAsked` |
| `question.replied` | bus（透传） | yes（用户答完立刻回 `.processing`） | dispatch 内联分支 |
| `question.rejected` | bus（透传） | yes（用户拒绝/取消后回 `.processingStarted`） | dispatch 内联分支 |
| `permission.asked` | bus（透传） | yes（审批条 / Always 的基础） | `handlePermissionAsked`，详见 `2026-07-10-opencode-permission-handling.md` |
| `serverPort` | **plugin 自造** | yes（0 = 无 HTTP server，即无 `--port` 的 TUI） | `handleServerPort` |
| `message.updated` | bus（透传） | yes（user 边界；`finish=stop` 只 flush） | `handleMessageUpdated` |
| `message.part.updated` | bus（透传） | yes（`text` / `reasoning` / `tool` / `file` / `step-start`；`tool=question` 是 DEFENSIVE 路径） | `handlePartUpdated` → `handleToolPart` |
| `message.part.delta` | bus（透传） | yes（`text` 与 `reasoning` 流式） | `handlePartDelta` |
| `file.watcher.updated` | bus（透传） | **no**：插件照转，adapter 的 dispatch `default` 丢弃 | — |

| 事件 | 结论 |
|---|---|
| `message.part.final` | opencode 不存在的 type |
| `session.status=ended` | opencode 只有 `idle` / `busy` / `retry` |
| `ask_user_question` | v1.15.x 起改名 `question.asked` |

## 关键陷阱

### 陷阱 1: `question.asked` 是 event 不是 tool call

opencode v1.15.x 早期文档把它描述成 "tool name = question"，**实际它是 Bus 顶层事件**，跟 `message.part.updated` 平级。Nook adapter 在两个地方检测：

1. **PRIMARY**：`handleQuestionAsked` 监听顶层 `question.asked`，产 `.waitingForUserInput`，并带上 `que_` 前缀的 `requestId`。
2. **DEFENSIVE**：`handleToolPart` 在 `state.status == "running"` 且 `tool` 为 `question` / `askuserquestion` 时，额外 emit 一条 `.waitingForUserInput`，与 `.preTool` 一起返回。

**两条路径不等价，不要当成互为替代：**

| | PRIMARY | DEFENSIVE |
|---|---|---|
| phase | `.waitingForInput` | `.waitingForInput` |
| `requestId` | 有（`que_xxx`） | **nil** |
| 用户能否在 Nook 里回答 | 能 | **不能**（`OpencodeQuestionReplyProvider.sendAnswer` 的 `guard let requestId` 会抛 `QuestionReplyError.missingRequestId`） |

所以兜底只保住「列表里显示正在等你」，保不住「能回答」。PRIMARY 不能降级、不能删。两条路径的 idempotent 只发生在 phase 层（重复设置同 phase 是 no-op）——若 `question.asked` 随后也到达，`SessionStore` 会把 `requestId` 合并进去。

### 陷阱 2: 早期观察 "v1.17.x 不发 `question.asked`" 是误判

2026-06-17 08:23 测试时观察到 `question.asked` 没到，初步判断 "v1.17.x 不发"。**同一天 08:36 复测时日志清晰显示 `[opencode] event type=question.asked` 正常到达**。根因是 opencode/plugin **socket 启动时序问题**（socket 没绑定），不是事件不存在。

教训：遇到"事件缺失"先看 transport（socket 绑定、plugin 启动顺序），不要急着改 handler 加 fallback。Fallback（陷阱 1 第 2 条）已经写好，作为 defense-in-depth 永远保留，但**不要**因为某个时序问题就把 PRIMARY 路径改成 secondary。

排查入口：`/tmp/nook-plugin-debug.log` 里搜 `command server listening`——没有这行说明 plugin 侧 transport 没起来，此时任何"事件缺失"都不是事件模型的问题。

### 陷阱 3: adapter 不消费 `file.watcher.updated`（**plugin 仍在转发它**）

> 2026-10-23 修正：初版写的是「Nook plugin 不转发它」，与代码不符，也与本文「决策档案」自相矛盾。

事实：

- `index.js` 的 `event` hook **没有白名单**，`file.watcher.updated` 与其它事件一样被转发（`type: event.type`）。当日日志中该事件出现 85 次，确实到达 Nook。
- 不做处理的是 **adapter**：dispatch 的 `default` 分支返回空数组，事件被丢弃。
- 它对 session 状态没有意义，所以「丢弃」是正确行为；但它仍然消耗一次 socket 连接 + 一行 adapter 入口日志（Debug log 开启时，dispatch 入口对**每个**事件无条件写一条 `event type=...`，不做类型过滤）。

用户如果在 debug log 里看到大量与 session 无关的事件（`file.watcher.updated` / `plugin.added` / `catalog.updated` …），那是 opencode 自己的 emit 行为经插件透传，**不是 Nook bug**。完整噪声清单见上文「插件透传的噪声」。

### 陷阱 4: `session.idle` 可能丢失（2026-10-23 事故；已用 `session.status=idle` 双路 + 静默兜底修复；源码依据取自本地 CLI 1.19.3）

实测（`docs/debug/2026-10-23-opencode-lost-idle-stuck-processing.md`）：
opencode 侧 `message.finish=stop` + `step-finish` 已落库、消息已结束，但 Nook 只收到最后一条
`message.part.updated(text)`，之后 `step-finish` / `message.updated(finish=stop)` / `session.idle`
**全部未到达**。其中前两条可从 sqlite 落库记录证明「事件已产生」，`session.idle` 是 ephemeral
bus event、不落库，因此无法区分「没发」还是「发了没送到」——能确认的只有「Nook 没收到」。
Nook 因此永久停在 `.processing`（opencode 进程仍存活，进程退出清理也不会触发）。

修复前的设计约束（历史）：

- `handleMessageUpdated` 在 `finish=stop` 时只 flush 文本，不 emit `.stop`（现状仍如此：它只负责把最后一段文本冲刷到 UI）。
- 当时 `handleSessionStatus(idle)` 只 flush，不产 `.stop`。
- 因此 `.stop` 当时只能由 `session.idle` 产生（`handleSessionIdle` 是单一构造点）——单点。
- plugin `send()` 是 best-effort：每条事件新建 socket，失败静默吞掉，无重试/ACK。
- 叠加「`session.idle` 每个会话每轮至多一次」的稀有性，单次传输失败就等于永久卡死。

**源码依据（本地 opencode 源码，CLI 1.19.3）**：

- `packages/opencode/src/session/status.ts` 的 `SessionStatus.set()` 在 `status.type === "idle"` 时，
  先 `publish(Event.Status, {status:{type:"idle"}})`，紧接着 `publish(Event.Idle, {sessionID})` ——
  `session.status=idle` 与 `session.idle` 是同一次调用产生的 **1:1 双发**。
- `packages/schema/src/session-status-event.ts` 里 `session.idle` 已标注 `// deprecated`。

已实施的冗余（2026-10-23，commits `5991426`…`cc747c8`）：

- `handleSessionStatus(idle)` 在 flush 之后**无条件额外产 `.stop`**（adapter 不持有 phase）。
- `handleSessionIdle` 保留为 legacy 路径：先 flush、再 `cleanupState`，最后产 `.stop`。
- phase 保护落在 `SessionStore.processOpencodeStop`：只有 `phase.isActive`（`.processing` / `.compacting`）才做「phase → `.idle`」+ 完成通知；
  `.waitingForInput` / `.waitingForApproval` / `.waitingForTerminalApproval` / 已 `.idle` 的会话不动。
- **清理逻辑无条件执行**（running tool → `.interrupted`、`toolTracker.inProgress` 清空、`publishState()`），等待态被 stop 时也要收尾。
- 完成通知用「每轮一次」闩锁 `opencodeCompletionNotifiedSessions`：在 prompt / `processingStarted` / TUI `.userPrompt` 时重置，会话注销时移除。
  它挡住 chat item 在两条 `.stop` 之间把 phase 拉回 `.processing` 造成的二次通知。

为什么不选 `finish=stop`：`finish` 是 message 级字段，每个 `step-finish` 都会用 provider 的 reason 覆写它
（`packages/opencode/src/session/processor.ts` 里 `ctx.assistantMessage.finish = value.reason`）；中间 step（工具调用后继续）的 reason 是
`tool-calls`，只有最后一步才是 `stop`。也就是说它不是「本轮结束」的稳定信号，而是跟着 step 走、还会被
`message.updated` 重复携带——用它驱动 `.stop` 需要额外去重与状态判断。

而 `status=idle` 与 `session.idle` 是**同一次调用**的双发（1:1），凡是会闪的 `session.idle` 同样会闪——所以改为
`status=idle` 驱动**不会新增闪烁面**，只是让丢失其中一条时仍有第二条可用。
注意二者出自同一个 `set()` 调用点：冗余的是**传输报文**，不是产生路径——同一个 `set()` 没被调用时两条一起没有，
这种情况只能靠静默兜底。

实现细节（已落地）：adapter 不持有 phase，`phase.isActive` 的判断落在 `SessionStore.processOpencodeStop`。
**guard 没有写成函数入口早退**：`processOpencodeStop` 在 phase 转移之前还会做「running tool → `.interrupted`」、
`toolTracker.inProgress.removeAll()`、`publishState()` 和完成通知；入口 guard 会让这些一并跳过。
只把「phase → `.idle`」与完成通知放在 `wasActive` 条件内，清理逻辑照旧执行（等待态被 stop 时也要收尾）。

**版本口径**：`status=idle` 只在 opencode ≥1.18 是轮末信号；v1.15.13 / v1.17.x 会在 tool step 之间发
`status=idle`，因此 idle→`.stop` 路径对 ≤1.17 **不支持**——这些版本依赖 `session.idle` + 90s 静默兜底。
旧版若丢失 `session.idle`，可能出现 step 间闪烁或无法按步通知。

**已实施的静默兜底**（`SessionStore.recheckAllSessions()`）：opencode active 会话 90s 无事件 → `.idle`；
`.compacting` / `waitingForApproval` / `waitingForTerminalApproval` / 有运行中或排队中的工具
（chat item 或 `toolTracker.inProgress`）时放宽到 600s。过期时清 `completionNotificationAt`、
把停滞工具（含 `waitingForApproval`）标 `.interrupted`、清 `inProgress`。
`.waitingForInput` **永不自动过期**。`session.status=retry` 与 `question.replied` / `question.rejected`
都映射成 `.processingStarted`，分别用于在 provider 退避和用户答完/拒绝后刷新 `lastActivity` / 退出等待态。

**已知残留风险**（详见 debug 文档「残留风险」）：

- 90s 窗口对长 TTFT / 非流式 reasoning / 排队中的 turn / `retry-after` header >90s 会误判；下一个事件会拉回 `.processing`，代价是一次闪烁。
- 审批 600s 过期会隐藏审批条，而 opencode 可能仍阻塞在权限请求上；用户需回 TUI 处理。
- `.waitingForInput` 只有 `question.replied` / `busy` / 新一轮 prompt 三个出口。
- ≤1.17 结束信号路径不支持（见上）。
- 最后一条 `.stop` 之后若再到达 chat item，可能把 phase 重新拉回 `.processing`，直到下一个静默窗口。

## 决策档案

- **`HookEvent.determinePhase()`**（`Nook/Models/SessionEvent.swift` 的 `HookEvent` 扩展，**不是** `SessionEvent` 的方法）里 `ToolKind.classify(tool) == .askUserQuestion` → 返回 `.waitingForInput`（不是 `.waitingForApproval`）。`SessionPhase` 加 `isWaitingForInput`（`#58202f5`）。
  注意：opencode 路径**不经过** `determinePhase()`——`.opencodeWaitingForUserInput` 在 `SessionStore.process` 里直接分派给 `processOpencodeWaitingForUserInput`。这条决策只影响 Claude hook 链路。
- **`MCPToolFormatter.toolAliases`** 加 OpenCode 小写映射（`question` → `Question` 等）（`#dadcfa3`）。
- **Adapter 不消费 `file.watcher.updated`** — 插件仍在转发，adapter 丢弃（见陷阱 3）。
- **`session.status=retry` 已消费（→ `.processingStarted`）** — provider 退避期间刷新 `lastActivity`；否则 90s 静默兜底会在重试中途误判为空闲。
- **`session.idle` 已被 opencode 标为 deprecated**（`packages/schema/src/session-status-event.ts` 里的 `// deprecated`），
  而 `session.status=idle` 是同一 `SessionStatus.set()` 调用里的主信号。Nook 侧不再把逻辑绑死在 `session.idle` 上：
  `session.status=idle` 与 `session.idle` 都会产 `.stop`，后者仅作旧版本兜底；丢失任意一条仍有另一条 + 静默兜底。

## 复测方法（每次 opencode 升级必做）

```bash
# 0. 设置里勾选 Debug log，然后真实跑一轮对话（不要用 curl 打本地 server）

# 1. 实际到达的事件类型与频次（本文件「噪声」表的取数方法）
grep -o "event type=[a-z.-]*" /tmp/nook-debug.log | sort | uniq -c | sort -rn

# 2. 关键事件是否到达
grep -n "event type=question.asked\|event type=session.idle\|→ stop\|→ waitingForUserInput" \
  /tmp/nook-debug.log | tail -20

# 3. transport 是否健康（事件"缺失"时先看这里）
grep -n "command server listening" /tmp/nook-plugin-debug.log | tail -3
```

判读：

- 一轮正常结束应看到 `→ idle (turn end)` 恰好一次；`session.idle` 到达时另有 `→ stop (legacy session.idle)`，两条都到由 store 的 `wasActive` / 通知闩锁去重。**若最后一条 text/`message.part.updated` 之后该 session 零事件，且 90s 内也没有被静默兜底降级，就是陷阱 4 复现**（不是乱序）。
- `question.asked` 缺失时，先确认第 3 步有 `command server listening`，再怀疑事件模型（陷阱 2 的教训）。
- 频次表里出现未登记的新事件类型 → 补进「插件透传的噪声」，并确认不是 Nook 需要消费的信号。
